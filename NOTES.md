## Phase 2 — Database

### P1001 on Neon

**Symptom**

```
Error: P1001: Can't reach database server at
`ep-gentle-mode-b2pxnzjl-pooler.c-6.eu-central-1.aws.neon.tech:5432`
```

**What it actually was:** the Neon compute was asleep. Neon suspends a free-tier
database after a few minutes of inactivity; the first connection has to wait for
it to boot, and Prisma's default connection timeout gave up before that finished.

**Fix** — append a longer connect timeout to `DATABASE_URL`:

```ini
DATABASE_URL="postgresql://…/neondb?sslmode=require&channel_binding=require&connect_timeout=15"
```

**The wrong diagnosis, kept on purpose:** the first guess was the pooler — that
`-pooler` in the hostname meant Prisma was hitting PgBouncer and needed the
direct endpoint instead. It wasn't that. The host still says `-pooler` and it
works fine. The clue that settled it: the *only* thing that changed was
`connect_timeout`, so the connection was never wrong, only impatient.

Worth generalising:

> **P1001 against Neon usually means the compute is cold, not that the connection
> string is broken.** Check whether the host is even reachable before you start
> rewriting the URL.

⚠️ `connect_timeout=15` is **not currently in `server/.env`.** It got dropped at
some point. If P1001 comes back, that's the first thing to re-add.

### Reading the init migration

`prisma/migrations/20260812115626_init/migration.sql`. This file is the only
place you see what Prisma actually did to the database. Read it before letting
anyone explain it — five things to find yourself:

1. Two `CREATE TABLE` statements
2. Where `email` gets its unique index — and note that it's a **separate statement**, not part of the table
3. The `CREATE INDEX` on `Post` — which column, and in which direction
4. The `FOREIGN KEY` constraint at the bottom, and the words `ON DELETE CASCADE`
5. What type `dateOfBirth` became versus what `createdAt` became

<details>
<summary><strong>Answers — open after you've had a go</strong></summary>

**1. The tables.** `User` and `Post`, each with `CONSTRAINT "X_pkey" PRIMARY KEY ("id")`
declared at the end of the table body. Note there's no `DEFAULT` on `id` in the
SQL: `@default(uuid())` is generated by *Prisma*, in Node, before the INSERT.
Postgres doesn't know about it. Insert a row with raw SQL and you must supply the
id yourself.

**2. The unique index.**

```sql
CREATE UNIQUE INDEX "User_email_key" ON "User"("email");
```

Separate because in Postgres a unique constraint *is* an index — uniqueness is
enforced by one. Prisma writes it as its own statement so it can be created,
dropped, or renamed independently of the table. That's also why a duplicate email
surfaces as a Prisma `P2002` error naming `User_email_key`, which is what you'll
catch and turn into the 409 in Phase 4.

**3. The Post index.**

```sql
CREATE INDEX "Post_createdAt_idx" ON "Post"("createdAt" DESC);
```

`createdAt`, descending. Not arbitrary: the feed's only query is
`ORDER BY createdAt DESC LIMIT 50`. A descending index means Postgres walks the
first 50 entries in index order and stops — no sort step, no full table scan.
An ascending index would still work (indexes can be scanned backwards) but
matching the direction is the honest expression of intent.

Also note: **no index on `authorId`.** Deliberate, for now. Nothing queries posts
by author yet. When "view a user's posts" gets built, that index goes in — and
you'll be able to measure the difference, which is the interesting part.

**4. The foreign key.**

```sql
ALTER TABLE "Post" ADD CONSTRAINT "Post_authorId_fkey"
  FOREIGN KEY ("authorId") REFERENCES "User"("id")
  ON DELETE CASCADE ON UPDATE CASCADE;
```

Three things at once:

- **Referential integrity.** A `Post` row cannot exist with an `authorId` that
  isn't a real `User.id`. This is the rule that rejected the made-up `authorId`
  in Studio. It is enforced by *Postgres* — application bugs, raw SQL, and
  someone poking at the database by hand all obey it. That's why it belongs here
  and not in your Express code.
- **`ON DELETE CASCADE`** — delete a user, their posts are deleted in the same
  transaction. The alternatives were `RESTRICT` (refuse to delete a user who has
  posted) and `SET NULL` (orphan the posts, which needs a nullable `authorId`).
- **`ON UPDATE CASCADE`** — if a `User.id` ever changed, the `authorId`s would
  follow. Prisma adds this by default. With UUID primary keys it will never fire,
  because ids don't change.

It's a separate `ALTER TABLE` at the bottom for ordering reasons: the constraint
references `User`, so `User` has to exist first. Emitting all tables and then all
constraints avoids Prisma having to work out a dependency order.

**5. The types — the interesting one.**

```sql
"dateOfBirth" DATE NOT NULL,
"createdAt"   TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
```

Both are `DateTime` in the Prisma schema. They became different Postgres types
because of `@db.Date`, and the distinction is real:

|  | `DATE` | `TIMESTAMP(3)` |
| -- | ------ | -------------- |
| Stores | A calendar day | An instant, to the millisecond |
| Timezone | Meaningless | Everything |
| Right for | Birthdays, holidays, invoice dates | Created-at, logged-in-at, anything that *happened* |

A birthday is the same day for everyone on earth. Store `1998-04-21` as a
timestamp and it becomes `1998-04-21T00:00:00Z`, and a user in UTC−5 renders
their own birthday as **20 April**. This bug is endemic and it always ships,
because it only shows up for users in a different timezone from the developer.

An account creation, by contrast, happened at one absolute moment, and you want
to be able to order and compare those moments across users anywhere.

The `(3)` is millisecond precision — JavaScript `Date` has exactly millisecond
precision, so storing more would be storing noise. And `DEFAULT CURRENT_TIMESTAMP`
means `createdAt` is filled in by **Postgres**, not Node — unlike `id`. The
database clock wins, which is the right call: it's one clock instead of however
many servers you end up running.

</details>

### Other Phase 2 things worth remembering

- **Prisma 7 does not read `.env` on its own.** That's what `prisma.config.ts`
  is for — `import "dotenv/config"` at the top, then `env("DATABASE_URL")` in the
  datasource block. In Prisma 6 and earlier this was automatic. If you follow an
  older tutorial and get "environment variable not found", this is why.
- **The generated client goes to `src/generated/prisma`**, per the `output` in
  `schema.prisma`, and that path is gitignored. It's a build artifact. Anyone
  cloning the repo runs `npx prisma generate` to recreate it — which means CI
  has to run it too, before typecheck, or Phase 8 fails on missing types.
- **`migrate dev` vs `db push` vs `migrate deploy`.** `migrate dev` writes a SQL
  file and applies it — local only. `db push` syncs the schema with no migration
  file, which is fine for scratch databases and wrong for anything you want a
  history of. `migrate deploy` applies existing files and writes none — the
  production one. Never run `migrate dev` against production; it can reset the
  database.
- **Migrations are committed, `.env` is not.** The migration folder is the
  database's version history and belongs to everyone. Verified on GitHub that
  `prisma/migrations/` is there and `.env` isn't.
